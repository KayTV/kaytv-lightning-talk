Securing the agent that fills your forms

Inside the security & privacy architecture behind the Form-Filling Assistant — an agentic tool that helps caseworkers complete benefit applications for real families.

Built with Riverside County Children and Families Commission & Amplifi · Evaluated by Georgetown's Better Government Lab · navapbc.com/labs

Source: Nava Labs, "Protecting personal data in AI-powered tools." Every detail below is pulled from the published case study on the Form-Filling Assistant's security & privacy architecture — built in partnership with the Riverside County Children and Families Commission and Amplifi, with evaluation support from Georgetown's Better Government Lab.

Why this talk

An agent with real access to real people's data

Form-Filling Assistant reads case records and fills out benefit applications across real government portals, then hands a caseworker a completed draft to review and submit. That's the whole value — and the whole risk surface.

Across a six-month pilot: zero privacy or security incidents, and 67% of caseworkers said they trust the tool most or all of the time. Four layers got us there.

  • No retention — the model reads client data, it never stores it.
  • Isolation — every session runs in its own contained browser environment.
  • No submit path — the agent can fill a form; it structurally cannot send it.
  • Caseworker control — a person watches, can take over, and reviews every field.

01 · Model & data retention

The model sees it — it never keeps it

The model is called through Google Cloud's Gemini Enterprise routing layer instead of a direct API connection — that routing is what rules out retention. A field like a name, a birth date, or a Social Security number gets read only as long as it takes to drop into the form, then it's gone. No one downstream keeps a copy or trains on it.

Fig. 1 — every field passes through once. Nothing about the client is kept on either provider's side.

  • One field at a time — the model only ever sees what it's currently populating, not the whole record.
  • Gemini Enterprise routing — every call passes through Google's management layer, configured to drop the data after, not log it.

02 · Session isolation

No two sessions ever touch

Instead of running locally, the tool spins up a fresh Chrome instance in the cloud for every session, hosted by Kernel (SOC 2 Type II certified) inside Google Cloud's FedRAMP High infrastructure — one isolated VM per session, nothing shared between them. That single browser serves two connections at once: Playwright drives it on the agent's side, while a live-view iframe mirrors the same screen for the caseworker in real time.

Fig. 2 — one browser session, two connections: Playwright drives it, a live iframe lets the caseworker watch every click as it happens.

  • Dedicated VMs — Kernel spins up a fresh virtual machine per session, with no shared memory or storage across them.
  • One screen, two viewers — the agent operates it, the caseworker watches the same feed live.

03 · No submit path

There's no button for the agent to press

We didn't want one safeguard carrying all the weight, so an unauthorized submission has to get past three independent ones before it could ever happen — and any single one of them failing still isn't enough on its own.

Fig. 3 — three independent safeguards, none of which the agent controls. The only path forward is a caseworker's own click.

  • System-prompt guardrail — the model's core instructions rule out ever clicking a submit control.
  • Nothing to call — there's no submit action in the tool's function set; finishing a form just produces a summary for review.

04 · Human oversight

The caseworker can take the wheel anytime

At any moment, a caseworker can step in mid-session. One click on "take control" halts the agent and whatever it was mid-way through doing; a click on "give back control" hands the browser back — the agent re-orients with a fresh screenshot and picks up from wherever the caseworker left things.

Fig. 4 — the caseworker can move between agent mode and full manual control as many times as needed, in either direction.

"That would be nice. I know we always talk about having to input the data again. This would save so much time for all of us." — Caseworker in California
  • Take control / give back control — either click instantly pauses or resumes the agent; nothing is lost mid-step.
  • Review card — every field is labeled by source: pulled from the case management system, entered manually, or auto-filled with an explanation the caseworker can check.

Since the pilot

Newer models, held to the same rules

That was all validated on Claude Sonnet 4.6 a few months back — we've since moved to newer, more capable releases, wrapped in Vercel's Eve as an execution harness. Eve catches malformed tool calls and retries failed steps, keeping a more improvisational model anchored to the same system-prompt guidance instead of letting it wander off-script.

Wrap-up

Four practices, in one sentence each

None of these four holds up alone — together, a leaked field, a missed check, or an off-script model still has to get through the rest before it reaches a real submission.

  • The model processes personal data — it never stores or trains on it.
  • Every session runs in its own isolated, FedRAMP High-grade environment.
  • The agent has no way to submit a form — only to prepare it for review.
  • A caseworker watches, can take over anytime, and reviews every field's source.

Result: 0 privacy or security incidents and 67% caseworker trust across a six-month pilot with Riverside County.
